## Codebase maps

### map:core-runtime — core runtime &amp; agent plumbing (packages/core/src: orchestrator, event-bus, agent-manager, agent-registry, agent-memory, session-manager, scheduler, mcp-manager, mcp-server, config, db)

Raven's runtime is a single Node process wired together by a 620-line boot sequence (`/home/user/projects/personal-assistant/packages/core/src/index.ts`) around one in-process `EventEmitter` wrapper (`event-bus/event-bus.ts`, 55 lines, `*` wildcard, `MAX_LISTENERS = 50`). Every emitted event is also INSERTed into the SQLite `events` table by a `*` listener registered at index.ts:119. The real chokepoint is NOT the Orchestrator — it is `AgentManager`, the sole subscriber of `agent:task:request`. The Orchestrator (`orchestrator/orchestrator.ts`, 399 lines) subscribes to exactly three event types (`email:new`, `user:chat:message`, `agent:task:complete`); at least eight other subsystems emit `agent:task:request` directly and bypass it (pipeline-executor, knowledge ingestion/lifecycle/clustering/hub-ops, create-validation-deps, the `execution:task:run-agent` bridge in index.ts:247, plus two suite services). Routing is 100% hardcoded event-type subscription plus one substring match on the user's message for the word "retrospective" (orchestrator.ts:174-192). There is no LLM router in code: `email:new` always goes to the `email` suite, `user:chat:message` always goes to `namedAgentStore.getDefaultAgent()` — which is hard-wired, with no per-session or per-project agent selection anywhere in the chat API or WebSocket handler, so only `projects/agents/raven/agent.yaml` ever handles user chat and `_agent-builder` / `system-admin` are unreachable from the UI.

The single place a Claude session is created is `runAgentTask` in `agent-manager/agent-session.ts` (462 lines). It picks a backend once at boot from whether `ANTHROPIC_API_KEY` is empty (`initializeBackend`, agent-session.ts:33): empty key → `cli-backend.ts` spawning `claude -p ... --dangerously-skip-permissions` with `CLAUDECODE: undefined`; non-empty → `sdk-backend.ts` calling `query()` with `permissionMode: 'bypassPermissions'`. Because the owner is on a MAX plan, the CLI backend is the production path. **Neither backend ever passes `resume` / `--resume`**, `SessionManager.linkSdkSession` has zero callers so `sessions.sdk_session_id` is always NULL, and `prompt-builder.ts` never includes the transcript — so every chat turn is a cold agent that sees only the current message. The tool that was supposed to fix this (`get_session_history`) lives in the Raven MCP, which is dead: `ravenMcpDeps` is never passed into `new AgentManager({...})` (index.ts:343-354), so the whole `mcp-server/` tree (7 files, 6 tool modules, 3 dedicated test dirs) never loads. Meanwhile the orchestrator unconditionally injects instructions telling the model to call `classify_request`, `create_task_tree` and `send_message` (orchestrator.ts:346-354) — tools that do not exist at runtime. The one memory mechanism that *does* work is `agent-memory/memory-store.ts` + `mcp-server/memory-mcp.ts`: an in-process MCP scoped to `projects/agents/<name>/memory/` with a YAML-declared budget, whose `MEMORY.md` index is injected into the system prompt (agent-session.ts:261-266) — but only when `task.namedAgentId` is set, i.e. only for chat turns and validation agents.

MCP isolation, the project's stated "critical rule", is nominal today. `sdk-backend.ts:27` passes *all* collected MCP server configs at the top level of `query()`, and agent-session.ts:279-284 adds an `mcp__<name>__*` wildcard to the parent's `allowedTools` for every one of them, with an explicit comment that this is required because "sub-agents inherit tools from the parent". What is actually isolated is narrower: each sub-agent *definition* names its own `mcpServers` subset. The default `raven` agent has `skills: []` + `isDefault: true`, which `agent-registry/agent-resolver.ts:84` resolves to the entire capability library — 14 sub-agents and 3 MCP servers (gmail, markdownify, ticktick) spawned on every chat turn. Three strata coexist and duplicate each other: the v1 legacy DB `schedules` table (now read by nothing; migrations 026/028/029 deleted its rows), the v2 suite registry (still the source of services, job handlers and pipeline agents), and the June-2026 filesystem layer (`library/` skills, `projects/**` agents/templates/schedules). Three separate workflow engines exist in parallel with literally duplicated definitions — `config/pipelines/morning-briefing.yaml` (cron 06:00) versus `projects/templates/morning-briefing.yaml` (fired 09:00 by `projects/schedules/morning-briefing.yaml`) — and the pipeline copy is broken because its nodes name skills (`gmail`, `ticktick`, `digest`, `telegram`) that are not suite names.

**Extensibility without code:** Partly yes, with a hard ceiling and one badly-placed trapdoor. WITHOUT writing TypeScript the owner can: add or edit agents by dropping projects/**/agents/<name>.yaml or <name>/agent.yaml (genuinely hot-reloaded — yaml-named-agent-store re-derives locations on every call — and git auto-committed by config-committer.ts); add capabilities by adding library/skills/<path>/{config.json,skill.md} plus library/mcps/<name>.json (each becomes a sub-agent definition with its own MCP subset via capability-library.ts); add task templates (projects/templates/*.yaml); add schedules (projects/schedules/*.yaml); add pipelines (config/pipelines/*.yaml); tune permission tiers (config/permissions.json); toggle suites (config/suites.json) and per-schedule enablement from the dashboard. Definitions are files, validated by Zod schemas, with `npm run validate:library` and `validate:projects` scripts — that part of the vision is real.

Where it breaks down, in order of severity. (1) Only the default agent is ever invoked. Orchestrator.handleUserChat calls getDefaultAgent() with no override path in the chat REST route, the WS chat:send payload, or the web client, so writing a new agent.yaml gets you an agent that nothing can talk to — including `_agent-builder` and `system-admin`, which exist today and are unreachable. (2) Its `model` and `maxTurns` are ignored (agent-session.ts:305-306 always uses the global config), so per-agent tuning is a no-op. (3) The self-extension story is written but not executable: projects/agents/_agent-builder/agent.yaml instructs the agent to `POST /api/scaffold/domain` and friends, but its allowedTools are Read/Glob/Grep/WebSearch/WebFetch with `bash: access: none` — it has no tool that can issue a POST. The scaffolding API (scaffolding-api.ts, scaffolding-routes.ts) is fully built and reachable only from curl or the web UI. (4) A `kind: job` schedule is only half-declarative: the YAML is data, but the handler must be registered in TypeScript (core-jobs.ts or a suite service calling context.jobRegistry.register), so a new recurring job that isn't a template still requires code. (5) New templates and schedules require a process restart — scaffolding-api.ts:196 reloads projectRegistry but nothing reloads TemplateRegistry or re-invokes scheduleEngine.start(), and the engine holds the schedule array by reference from boot. (6) Anything touching the event vocabulary (a new RavenEventType), a new routing rule, a new service integration (IMAP-style watcher, bot), or new Raven MCP tools is TypeScript-only. Net: adding an agent or a skill is a file edit; making that agent reachable, giving it the right model, or letting it extend the system on the owner's behalf currently is not.

**Key findings:**
- Event flow, concretely: trigger (Telegram bot / IMAP watcher / croner / HTTP POST /api/projects/:id/chat / WS chat:send) -> eventBus.emit -> the '*' listener at index.ts:119 INSERTs into the events table -> a typed subscriber. For chat: Orchestrator.handleUserChat ensures a DB project row, gets or creates a session, appends the user message to the JSONL transcript, resolves capabilities from the default named agent, stacks four '[System: ...]' blocks onto the message, and emits agent:task:request. AgentManager priority-inserts it (urgent/high/normal/low) and runs up to 3 concurrently. runAgentTask builds allowedTools + sdkMcpServers + systemPrompt and calls the CLI or SDK backend; streamed assistant text and tool calls fan out to both the JSONL transcript and agent:message events (which the WS handler forwards to subscribed browser channels). On finish AgentManager emits agent:task:complete, which the Telegram bot turns into a reply and which triggers the compaction check.
- Routing is entirely hardcoded event-type subscription — there is no LLM router in code. The only decisions are: email:new -> the `email` suite unconditionally (orchestrator.ts:104-137); user:chat:message -> namedAgentStore.getDefaultAgent() unconditionally (orchestrator.ts:225); and a literal substring test for 'retrospective' / 'summarize this session' / 'run retrospective' (orchestrator.ts:174-192). Neither the chat REST route, the WS chat:send message, nor the web client can select an agent, so `raven` is the only agent that ever handles user chat and `_agent-builder` / `system-admin` are unreachable from any interface.
- The LLM-routing design does exist — it is just not connected. Every chat prompt carries 'call classify_request with the appropriate mode ... For PLANNED: call create_task_tree ... then send_message' (orchestrator.ts:346-354), and those tools are implemented in mcp-server/tools/. But `ravenMcpDeps` is never passed to AgentManager (index.ts:343-354), so the tools never load. The model is instructed on every single turn to call tools that will not be in its tool list. Commit 09a07d4 ('remove upfront prompt injection — agents pull context via MCP') removed the working text-based fallbacks in favor of this path.
- Claude sessions are created in exactly one function — runAgentTask in agent-manager/agent-session.ts — configured with: systemPrompt from buildSystemPrompt (+ MEMORY.md block), allowedTools = 5 read-only tools + Bash-if-permitted + one mcp__X__* wildcard per server + 'Agent', model = config.CLAUDE_MODEL, maxTurns = config.RAVEN_AGENT_MAX_TURNS, cwd = projectRoot, permissions bypassed. Backend choice is made once at boot from whether ANTHROPIC_API_KEY is empty; on the owner's MAX plan that means the CLI backend spawning `claude` per task. Sessions are never resumed and sdk_session_id is never persisted.
- Agent memory is implemented well and IS used, but narrowly. memory-store.ts + memory-mcp.ts give each named agent a budgeted flat file directory at projects/agents/<name>/memory/ with memory_read/write/update tools and its MEMORY.md index injected into the system prompt (agent-session.ts:261-266). It is the only working continuity mechanism in the system. It is gated on task.namedAgentId, so it reaches chat turns and validation agents only — not pipeline nodes, task-tree agents, email triage, ingestion or knowledge agents. In practice the raven index is still the placeholder '- (no memories yet)', and nothing in the prompt actively instructs the agent to record anything.
- MCP isolation in practice: the main agent DOES receive every MCP server as a spawned subprocess and every mcp__X__* wildcard in its allowedTools, deliberately, so that sub-agents can inherit them. What is genuinely isolated is per-sub-agent scoping — suite-registry.ts:120 and capability-library.ts:125 each set `mcpServers: [...]` on the individual SubAgentDefinition. For the default raven agent that means 3 MCP subprocesses (gmail, markdownify, ticktick) and 14+1 sub-agent definitions on every chat turn, with the parent able to call all three MCPs directly.
- mcp-server/ is Raven exposing itself as an in-process SDK MCP (createSdkMcpServer, name 'raven') so that agents can drive Raven's own primitives instead of being fed injected text: classify/plan (classify_request, create_task_tree, escalate_to_planned), task lifecycle (get_task_context, complete_task, fail_task, update_task_progress, save_artifact), conversation (send_message, get_session_history), knowledge (search/save_knowledge, get_knowledge_context), validation (submit_validation_score), self-administration (list/create/update_agent, list_projects, trigger_pipeline) and human-in-the-loop (request_approval, which polls pending_approvals for 5 minutes). scope.ts gates tools by role (task/chat/system/validation/knowledge). It is architecturally the most modern part of the codebase and 100% dead at runtime.
- Wiring the Raven MCP is the single highest-leverage fix available: it would simultaneously restore multi-turn chat memory (get_session_history), close the task-tree completion loop (complete_task/fail_task), make the classify_request instructions in every chat prompt truthful, enable agent self-administration without shelling out, and give the validation agents their scoring tool. The change is roughly one object literal in index.ts plus fixing resolveAgentRole to key off namedAgentId.
- Scheduling is now genuinely unified and is the healthiest subsystem: 9 YAML files in projects/schedules/ drive croner via schedule-engine.ts, with kind:job resolved through JobRegistry (3 core + 4 registered by suite services) and kind:template resolved through TemplateScheduler; per-schedule enable/disable is a DB override in the preferences table; /api/schedules is a single surface over the engine. The v1 DB `schedules` table and legacy Scheduler are fully retired (commit 8122952, migrations 026/028/029). Two loose ends: kind 'agent' is typed but unimplemented, and the engine holds the schedule array by reference from boot so new YAML needs a restart.
- Persistence is spread over four stores with the DB holding runtime state only: SQLite /data/raven.db (30 migrations; sessions, agent_tasks, events, tasks, task_trees, execution_tasks, audit_log, pending_approvals, pipeline_runs, notification_*, insights, financial_*, preferences, projects), Neo4j (knowledge graph, hard boot dependency), JSONL files under data/sessions/<id>/ (transcripts + raw SDK output), and the filesystem for all definitions (projects/**/*.yaml, library/**, config/*.json, config/pipelines/*.yaml). The declared philosophy is honored for agents and schedules; the `projects` table is the notable violation, duplicating the filesystem hierarchy with a name-string bridge.

### map:engines — packages/core/src "engine sprawl" — task-execution, task-manager, pipeline-engine, template-engine, capability-library, scaffolding, knowledge-engine, insight-engine, notification-engine, permission-engine, bash-gate, config-history, project-manager, project-registry, suite-registry (+ scheduler/, which is inseparable from the work-unit question), and the declarative config under config/, library/, projects/

Three strata coexist in this area and none of them was ever removed. The v1 stratum is `suite-registry/` + `task-manager/` + `pipeline-engine/`, keyed off `config/suites.json`, `config/task-templates/*.yaml`, `config/pipelines/*.yaml`, and `suites/*/{actions,schedules}.json`. The v2 "capability library" stratum is `capability-library/` + `project-registry/` + `template-engine/` + `task-execution/` + `scheduler/`, keyed off `library/skills/**` and `projects/{agents,templates,schedules}/`. A June-2026 "control center" layer added `scaffolding/`, `config-history/`, and the unified `scheduler/`. All three are instantiated at boot in `packages/core/src/index.ts` (621 lines, one `main()` with `eslint-disable max-lines-per-function, complexity`), so "wired into the live system" is true of nearly everything — but wired is not the same as working, and the most important new path is wired at the front and dead at the back.

The decisive finding is that the v2 execution path cannot complete a unit of work. `TaskExecutionEngine.onTaskCompleted()` — the only method that advances a tree, unblocks `blockedBy` dependents, runs validation, or marks a tree finished — has exactly one caller in the entire repo: `packages/core/src/mcp-server/tools/task-lifecycle.ts:107`, inside the in-process Raven MCP. That MCP is created in `agent-session.ts:241` under `if (opts.ravenMcpDeps)`, and `index.ts` never passes `ravenMcpDeps` when constructing `AgentManager` (index.ts:~430). No event listener substitutes: of the thirteen `agent:task:complete` subscribers, none belongs to `task-execution/`. So a template fires, a tree is created and started, `execution:task:run-agent` is bridged to `agent:task:request` at index.ts:247-280, the agent runs — and nothing ever reports back. Trees stay `running` forever. The same missing `ravenMcpDeps` also kills all six modules in `mcp-server/tools/` and leaves the knowledge sub-agent (`knowledge-engine/knowledge-agent.ts`) with `tools: []`, a prompt naming three MCP tools that don't exist, and an explicit instruction not to use WebFetch instead. Compounding it, that same bridge hardcodes `skillName: 'orchestrator'` and `mcpServers: {}` and silently drops the `agent` field it destructures, so every template-declared `agent: gmail` / `agent: ticktick` task would run as a generic agent with no MCPs, no sub-agents, and no Bash even if the loop closed.

By contrast the legacy pipeline engine is the better-wired executor — `pipeline-executor.ts:209-226` resolves real MCPs via `mcpManager.resolveForSuite()` and real sub-agents via `suiteRegistry.collectAgentDefinitions()` — but its declarations are stale: `config/pipelines/morning-briefing.yaml` names `skill: gmail|ticktick|digest|telegram` while suites were renamed to `email|task-management|daily-briefing|notifications` (`packages/shared/src/suites/constants.ts`), so `suiteRegistry.getSuite('gmail')` returns undefined and every node fails with "Suite not found". It is `enabled: true` on cron `0 6 * * *`. Meanwhile `config/pipelines/system-maintenance.yaml` (cron `0 2 * * 0`) and `projects/schedules/system-maintenance.yaml` (cron `0 2 * * 0`, `run.kind: job`) both resolve correctly and fire the same `_orchestrator` maintenance work at the same instant from two independent cron systems. Migrations 026 and 029 show the team already fought this exact double-firing class of bug by deleting rows from the legacy `schedules` table; the pipeline-vs-schedule overlap is the same bug one layer up, unaddressed.

**Extensibility without code:** "Extend without writing TypeScript" is the stated mission and it is the weakest axis of this area today. On paper the story is complete: drop a YAML in projects/templates/ for a workflow, one in projects/schedules/ for its cron, one in projects/agents/ for a specialist, edit config/suites.json to toggle integrations, config/permissions.json to retune tiers, config/pipelines/*.yaml for DAGs — and have the _agent-builder agent do all of it for you through POST /api/scaffold/*, with git history and revert in the UI. Every one of those files exists and every loader is real.

In practice four breaks stack up. First, authoring a template is authoring into a dead engine: the tree it produces never completes (missing ravenMcpDeps), and its per-task `agent:` field is dropped by the bridge at index.ts:247-280, so even a completing task would run with no MCPs. Templates are the primary code-free authoring surface and they are the least functional. Second, nothing hot-reloads: templateRegistry.load() and scheduleEngine.start() are called once each in index.ts, so a hand-written or scaffolded template/schedule does nothing until the owner restarts core — which quietly makes "extend without code" mean "extend, then restart the daemon," and makes the _agent-builder's own instructions ("VERIFY — Confirm what was created") unverifiable. Pipelines are the exception and prove the point: pipeline-loader.ts watches its directory and reloads live, which is why the legacy format is the only one that behaves the way the whole system is supposed to. Third, the code-free path is unversioned and invisible: scaffolding-api.ts never calls gitAutoCommit, and config-history is hard-scoped to config/ (git-history.ts:11), so nothing authored under projects/ appears in the Config History UI or can be reverted there — even agent YAML edits, which ARE auto-committed by config-committer.ts, are invisible to the viewer built to show them. Then there is the authoring burden itself. A new recurring workflow requires the owner to know which of nine definition formats to pick, that a template's cron lives in a different directory than the template, that skill names in pipelines must match suite constants in packages/shared/src/suites/constants.ts rather than the names in config/skills.json, that run.kind:'agent' is accepted and silently never fires, and that a library skill's actions get no permission tier and therefore default to red. Failures are warn-and-continue across the board (loadTemplatesFromDir, ProjectRegistry.load, capabilityLibrary.load), and the one real validator — project-validator.ts, the largest file in project-registry — never runs at boot. So the most likely outcome of a code-free edit today is silence: no error, no effect, boot logging success.

Two things genuinely do work code-free and should anchor the fix. Adding a projects/schedules/*.yaml against an already-registered job ref is reliable, because schedule-engine.ts refuses to arm an unregistered handler and logs a warn instead of failing silently. And enabling/disabling a schedule from the UI persists through schedule-prefs.ts without touching a file. That is the shape the rest of the area needs: one declarative format per concept, a typed dispatch over named handlers, refusal-with-a-warning instead of silent no-op, boot-time validation, and hot reload on the directory that is the source of truth.

### map:capabilities-suites — Extensibility model — suites, capabilities, skills (how integrations and automated behaviours are defined today)

Raven today runs **two complete, overlapping integration systems side by side**, and the newer one silently won. The v2 `library/` capability library (`library/mcps/*.json` + `library/skills/<domain>/<category>/<name>/{config.json,skill.md}` + `library/vendor/` submodules) is what actually reaches the AI at runtime: every agent definition on disk (`projects/agents/*/agent.yaml`, `projects/system/agents/*.yaml`) carries `skills: []`, and `yaml-named-agent-store.ts:64` hardcodes `suiteIds: []`, so `agent-resolver.ts:83-86` takes the `hasNoBindings` branch and calls `resolveFromLibrary(capabilityLibrary)` with no filter — handing the orchestrator all 15 library skills as sub-agents, with flat MCP names (`ticktick`, `gmail`, `markdownify`) and vendor plugin paths. ### map:api-web-ux — API surface (packages/core/src/api), web dashboard (packages/web/src), and the Telegram interaction path — i.e. everything the owner actually touches to talk to Raven and see what it's doing

The API layer is a single Fastify app (`packages/core/src/api/server.ts`) that registers ~28 route-group files plus one WebSocket handler and one SSE stream. Almost every route group is gated behind an optional dependency (`if (deps.taskStore && ...)`), so the actual surface area boots up differently depending on which subsystems core wired up — this is the seam where v1/v2/v3 strata show through. There is no auth, no versioning, and no per-route access control; it's a single-tenant control plane for one owner.

Chat is unified end-to-end around one event: `user:chat:message` on the event bus. Three ingress paths write the identical event shape — POST `/api/projects/:id/chat` (routes/chat.ts, 20 lines, pure passthrough), the WebSocket `chat:send` message (ws/handler.ts), and the Telegram bot's `bot.on('message:text', ...)` handler (suites/notifications/services/telegram-bot.ts). The orchestrator consumes all three the same way, and responses flow back out over `agent:message` / `agent:task:complete` events, which the WS handler rebroadcasts verbatim to subscribed browser clients and which the Telegram service also subscribes to directly to edit/delete its "Processing..." status message and post the final answer. This is a genuine architectural strength: one event contract, three front doors, no duplicated logic. Real-time delivery to the browser is almost entirely WebSocket-broadcast-and-filter (client subscribes to `project:<id>` or `global`, server does no server-side type filtering, just channel routing) or REST polling (`usePolling`, used by ~10 of the 16 pages) — genuine SSE is used in exactly one place (`/api/agent-tasks/:id/stream`, consumed by `AgentMonitor`/`TaskDetail.tsx`), and I found one page (`/config`) that opens an `EventSource` against `/api/sse/events`, an endpoint that is never registered anywhere in the server — that page's "real-time updates" are dead on arrival with no polling fallback.

The web dashboard is a Next.js app-router SPA: 14 sidebar-linked pages, one dynamic `/projects/[id]` hub with 6 tabs (Overview/Tasks/Agents/Templates/Knowledge/Sessions), plus two pages reachable only by typing the URL (`/config`, and `/task-trees` which is now a client-side redirect shim to `/tasks`). State is split across four small Zustand stores (app-store for cross-cutting projects/skills/schedules/templates/health; task-store for the unified board; agent-store; knowledge-store) with no shared cache layer — most pages just poll their own REST endpoint independently. The owner can genuinely do a lot without touching code: create/edit projects, chat per-project, create/edit named agents, trigger task-tree templates with parameters, trigger/monitor pipelines, browse and revert config via git history, snooze-adjacent controls (server-side only, see below), and — notably — have the chat agent generate a pipeline YAML inline and hit Save right there in the chat bubble (`ChatPanel` → `PipelinePreview` → `PUT /api/pipelines/:name`), which is the one clean instance of "extend without writing code, and without leaving chat" working as the mission describes. But a whole tier of the system — the "capability library" style domain scaffolding (`ScaffoldingApi.scaffoldDomain`, bulk-creates projects+agents+templates+schedules as YAML on disk) — is registered as a live route (`POST /api/scaffold/domain`) and has a typed client method (`api.scaffoldDomain`) but is called from nowhere except unit tests; there is no UI entry point and no evidence any agent tool invokes it either, so this half of "extend without code" exists only at the API layer, invisible to the owner.

**Extensibility without code:** "Partial, and inconsistent across features. Genuine no-code extension paths that work today: (1) creating a named agent via the Agents page or a project's Agents tab (writes through NamedAgentStore, POST /api/agents) — no YAML/code needed, though the per-project scoping is not honored on read; (2) triggering a task-tree template with typed parameters from the Templates page; (3) asking chat to draft a pipeline and clicking Save on the inline YAML card, which PUTs straight to the pipeline engine — the cleanest 'ask for it in chat, it becomes a running capability' loop in the app. Extension breaks down as soon as you need anything the dashboard doesn't have a page for: there is no UI to define a brand-new suite/skill (only config/suites.json + a filesystem directory, hand-edited), no UI to scaffold a whole new project domain even though the backend (ScaffoldingApi.scaffoldDomain) supports doing exactly that in one call, no UI to review or resolve permission approvals or the audit trail (Telegram-only), and the Settings page's own guidance for enabling/disabling capabilities points at a config file (config/skills.json) the current boot sequence doesn't load. So the honest line today is: adding an agent, a template, or a pipeline is code-free and dashboard-native; adding a new suite/skill, a new project 'domain' with its own agents+schedules, or touching anything permission/approval-related still requires either hand-editing files on disk or talking to Telegram, not the web dashboard."

## External research

### research:openclaw-gateways — OpenClaw and Claude-native personal assistant gateways: architecture patterns for Raven (state of the art, August 2026)

OpenClaw (Warelay → CLAWDIS → Clawdbot → Moltbot → OpenClaw, by Peter Steinberger, Nov 2025 → present) is now the de facto reference architecture for self-hosted personal AI assistants: ~385k GitHub stars, ~81k forks, MIT, governed by the non-profit OpenClaw Foundation after Steinberger joined OpenAI in Feb 2026. Its central architectural bet is the inverse of Raven's: **it invested almost nothing in orchestration and almost everything in infrastructure primitives.** There is no event bus, no DAG, no planner tree, no manager-of-managers. VISION.md explicitly bans "agent-hierarchy frameworks (manager-of-managers / nested planner trees) as a default architecture" and "heavy orchestration layers that duplicate existing agent and tool infrastructure" from ever being merged. Instead there is one long-lived **Gateway** daemon on `127.0.0.1:18789` that owns every messaging channel, every session, the scheduler, the tool policy, and one typed WebSocket protocol (TypeBox → JSON Schema → generated Swift/Kotlin models). Everything else — CLI, TUI, web Control UI, macOS/iOS/Android apps, headless device "nodes" — is just a client of that protocol. The agent loop itself is a thin, swappable component: it began as a wrapper around external CLIs, then embedded Mario Zechner's minimal `pi` runtime (Read/Write/Edit/Bash), and is now vendored as `packages/agent-core` — only **5,851 lines**, out of ~417k non-test lines in the repo. External harnesses (Claude Code, Codex, Gemini CLI, Cursor, OpenCode) remain pluggable through three explicit seams: plugin-registered embedded harnesses, ACP (Agent Client Protocol), and text-only CLI backends. The lesson is not "use someone else's agent loop" — it is "the agent loop is 1.4% of the problem; sessions, channels, queueing, scheduling, memory, skills, approvals, and sandboxing are the other 98.6%."

What OpenClaw got most right, and what a from-scratch orchestrator like Raven almost inevitably reimplements poorly, clusters in five areas. **(1) Extension without code**: a skill is a directory with a `SKILL.md` — YAML frontmatter plus prose — discovered from six precedence-ordered roots, gated at load time by declarative predicates (`requires.bins`, `requires.env`, `requires.config`, `os`), auto-exposed as a slash command and as a `$name` prompt reference. No package.json, no tsconfig, no workspace registration, no build. Raven's skills are TypeScript classes requiring a new npm workspace and a compile step, which directly contradicts the owner's stated requirement to extend without writing code. **(2) A properly factored proactive stack**: five distinct mechanisms with a documented decision table — heartbeat (approximate, batched, main-session, with a monitor "scratch" checklist), automations/cron (exact timing, isolated sessions, task records, run history), standing intents (event-conditioned prospective memory compiled into SQLite rows with deterministic FTS matching, fire budgets, cooldowns and expiry — no model call in the match path), hooks (lifecycle scripts), and standing orders (permanent operating authority injected every session). Raven's single "proactive-intelligence suite" plus scheduler collapses five different problems into one. **(3) A memory architecture with a security model**: plain Markdown tiers (`AGENTS.md`/`SOUL.md` instructions, `MEMORY.md`/`USER.md` curated core, `memory/YYYY-MM-DD.md` episodic, standing intents prospective) over one SQLite index carrying **unforgeable provenance columns** (`owner`/`agent`/`untrusted`/`system`) that classification code writes and the model cannot write through prose. Promotion into the curated tier happens only via a background "dreaming" consolidation pass behind deterministic gates; untrusted-origin content is *structurally* barred from auto-injection regardless of recall frequency. The design is explicitly cited to LongMemEval, Generative Agents, sleep-time compute, PrefEval, TriggerBench, and MINJA/OWASP ASI06. **(4) The main-session model**: one rolling conversation keyed `agent:<id>:main` that all DM channels collapse into, with group sessions isolated but their activity flowing up as coalesced notices, and background work reporting results back to the session that spawned it. That is exactly the "central brain of my life" topology, and it is a session-routing rule, not an orchestration framework. **(5) Governed self-improvement**: Skill Workshop is a proposal queue (`PROPOSAL.md`, hash-bound to the live target, security-scanner-gated at apply, rollback metadata written before the live write, 30/90-day curator staleness lifecycle) and self-learning writes only through it — default mode `auto` for new skills, but update proposals always stay pending for human review.

Its weaknesses are equally instructive, and three of them are direct warnings for Raven. **Cost**: the 30-minute heartbeat originally shipped sending the full main-session context every tick — press and users reported ~$0.75 per idle check at 120k tokens, $18.75 in a single night, ~$250/week doing nothing, and one magazine burned $100 in a day. OpenClaw's fixes are now config knobs Raven should copy pre-emptively: `lightContext`, `isolatedSession`, `activeHours`, cheap-model override, empty-scratch skip, and busy-deferral. **Security**: prompt injection via Gmail and via Telegram/Discord link previews (PromptArmor demonstrated zero-click exfiltration through attacker-controlled URL query params), ~42,000 internet-exposed gateways with ~63% running port 18789 without auth, and a ClawHub supply-chain wave of ~824 malicious skills (~20% of the marketplace at discovery) shipping credential exfiltration, backdoors, and cryptominers. Notably, OpenClaw's SECURITY.md declares prompt-injection-without-a-boundary-bypass **out of scope by policy** — the trust model is "local-first infrastructure for a single trusted operator," which happens to be exactly Raven's deployment, so Raven inherits both the model and the residual risk. China restricted state enterprises and banks from running it in March 2026. **Chaos and scale**: 3.4k open issues; the project's own maturity scorecard self-rates 68% ("Alpha") with 6% end-to-end coverage across 50 surfaces and 281 capability areas; `extensions/telegram` alone is ~60k lines — more than most complete personal assistants. Raven must copy OpenClaw's *patterns* and refuse its *scope*.

Close cousins confirm the pattern has converged. **Hermes Agent** (Nous Research, released Feb 2026, ~175k stars) is nearly isomorphic: one gateway across 20+ channels, six execution backends (local/Docker/SSH/Daytona/Singularity/Modal), Tier-1 `USER.md`/`MEMORY.md` loaded into every session with zero retrieval latency, FTS5 cross-session recall, cron delivery to any platform, and agent-authored skills on the same open **agentskills.io** standard OpenClaw follows — the two projects even ship migration importers for each other. **claude-gateway** (0xMaxMa, ~22 stars) is the closest analogue to Raven's actual stack: it spawns one isolated `claude` CLI subprocess per chat, assembles `AGENTS.md` + `IDENTITY.md` + `SOUL.md` + `MEMORY.md` into a generated `CLAUDE.md` system prompt on file change, persists JSONL plus SQLite FTS5, and adds channels by implementing a `ChannelModule` interface — useful as a minimal reference, but its small scale illustrates the ceiling of the "wrap the CLI subprocess" approach: you do not own the tool loop, the transcript, the context assembly, or the hooks, which is precisely where all of OpenClaw's leverage lives. Raven's own note that the Claude CLI backend "can't run inside Claude Code sessions (CLAUDECODE env check blocks nesting)" is a concrete instance of that fragility, and mirrors OpenClaw's own guidance that CLI backends are "a safety net for 'always works' text responses, not a primary path."

**Recommended adoptions:**
- MAKE MARKDOWN THE PRIMARY EXTENSION UNIT. Replace the six-step TS-class-plus-npm-workspace-plus-build flow for adding a skill with a `SKILL.md` directory discovered from precedence-ordered roots (`data/skills/` → project skills → bundled), hot-watched, auto-registered as both a slash command and a `$name` prompt reference, following the AgentSkills spec so the owner writes the same format they already know from Claude Code. Keep `RavenSkill` TS classes strictly as the escape hatch for capabilities that genuinely need runtime hooks, a new provider, or a channel. This is the single change that most directly satisfies the stated requirement to extend without writing code, and it is why OpenClaw has ~50 bundled skills plus a whole registry while Raven has nine hand-built suites.
- GATE SKILLS DECLARATIVELY AT LOAD TIME, NOT WITH AN ENABLED FLAG. Replace `config/skills.json`'s `enabled: true` with frontmatter predicates — `requires.bins`, `requires.env`, `requires.config` (dot-path into config must be truthy), `os` — so a skill whose binary or API key is missing simply never enters the prompt instead of failing at boot. Keep visibility (per-agent allowlists) as a SEPARATE control from location/precedence. Raven's TickTick token saga is exactly the failure this prevents.
- RETIRE THE EVENT BUS AS A ROUTING MECHANISM; ADOPT LANES PLUS QUEUE MODES. Serialize runs per session key in a FIFO lane, cap overall parallelism with a global lane, and implement the four queue modes for messages arriving mid-run: `steer` as default (fold the new message into the active turn at a tool-call boundary), `followup`, `collect` with `debounceMs`/`cap`/`drop:"summarize"`, and `interrupt`. Fire typing indicators on enqueue so waiting is invisible. This is what Raven's collisions actually need, it is a fraction of the code of an event bus, and `steer` is the difference between an assistant that feels alive on Telegram and one that ignores you mid-task.
- ADD AN EXPLICIT MAIN SESSION ABOVE THE PROJECT HIERARCHY. Key it `agent:main`, collapse every DM channel (Telegram, web) into it, keep project/group contexts isolated but flow their activity UP as notices COALESCED PER CONVERSATION (never one wake per message), name the watched sessions in the system prompt, and have background work report results back to the session that spawned it. Raven's v2 project hierarchy risks fragmenting the brain into per-project silos with no convergence point; a main session is the 'central brain' topology and is a routing rule, not a framework.
- SPLIT THE PROACTIVE LOOP INTO FOUR DISTINCT MECHANISMS. Raven's single scheduler plus 'proactive-intelligence' suite conflates four different problems. Build: (a) HEARTBEAT — approximate, batched, main-session, driven by a small editable monitor checklist; (b) AUTOMATIONS — exact cron/one-shot in isolated sessions, persisted with run history, each run producing a task record; (c) STANDING INTENTS — event-conditioned; (d) HOOKS — lifecycle scripts. Publish a decision table so future-you knows which to reach for. OpenClaw's own docs are the template.
- SHIP HEARTBEAT COST CONTROLS AS DEFAULTS, NOT OPTIONS. Before the loop runs once: `lightContext` (skip workspace bootstrap files), `isolatedSession` (fresh session, no conversation history), `activeHours` with timezone, a cheap-model override, skip-if-checklist-is-effectively-empty, and busy-deferral (skip while the main queue, another run, or the target session is active). Add the ack contract: reply `HEARTBEAT_OK` or call a `heartbeat_respond` tool with `notify:false|true`, strip the token and drop the message if the remainder is trivial, and never let heartbeat replies extend session idle/daily freshness. The naive version of this loop is what produced OpenClaw's $250/week idle-cost reports; on a MAX plan Raven pays in exhausted quota instead of dollars, which is worse.
- COMPILE REMINDERS OUT OF THE MODEL. Time-based intents become cron rows the moment they are uttered. Event-based intents become SQLite rows with machine-checkable trigger keywords, channel/sender scope, expiry, fire budget, and cooldown, matched by a deterministic FTS prefilter on each turn with NO model call in the match path, bounded to ≤256 candidates and ≤3 injections per turn, with an explicit lifecycle (pending/armed/fired/done/cancelled/expired) and cancellation that is always explicit and never inferred. Defaults: 24h cooldown, 3 fires, 90-day expiry. Prospective recall degrades sharply with context length while retrospective recall stays fine, and models cannot be trusted to infer cancellation — do not store 'remind me when X' as prose and hope.
- BUILD THE TIERED MEMORY ARCHITECTURE WITH UNFORGEABLE PROVENANCE. Four tiers: human-only instructions (`AGENTS.md`, `SOUL.md`) / curated core (`MEMORY.md`, `USER.md`, always injected within budget) / episodic (`memory/YYYY-MM-DD.md`, never injected, searchable) / prospective (intents + cron). Store origin class as a SQLite ENUM COLUMN written by classification code — `owner`/`agent`/`untrusted`/`system`, never defaulting to `owner`, never parsed from prose — plus session kind, observed timestamp, and a supersession key. Then enforce the two hygiene rules that matter most for an always-on assistant: cron/heartbeat/subagent sessions produce NO durable memory candidates, and content injected from memory is marked and never re-extracted. Restrict auto-injection to the curated tier as a hard security rule. Raven ingests Gmail, files, and Telegram; without this, attacker-authored text reaches the prompt and eventually the curated core.
- WRITE DURABLE MEMORY FROM ONE BACKGROUND CONSOLIDATION PASS, NEVER FROM THE REPLY PATH. Score candidates deterministically (relevance, recall frequency, query diversity, recency, multi-day recurrence), exclude untrusted/system origins structurally BEFORE building any prompt, then let one bounded model turn rewrite the curated file — accepting the output only if it validates, stays in budget, and does not drop more than a bounded fraction of existing entries, otherwise falling back to append-only. Use optimistic concurrency (re-check the content hash immediately before an atomic rename), store a pre-image, and append a human-readable summary to a review file. Assign importance (1-10) and trigger phrases AT WRITE TIME as trailing comments so recall needs no query-time model call. Also: make `USER.md` imperative directives that supersede in place — Raven's feedback notes currently append and will drift into contradicting itself.
- GOVERN SELF-IMPROVEMENT WITH A PROPOSAL QUEUE BEFORE ENABLING ANY OF IT. Agent-authored skills write `PROPOSAL.md`, never the live file. Bind updates to the target's content hash so they go stale if a human edits first. Re-run a security scan immediately before the live write. Write rollback metadata BEFORE touching live files. Confine writes to the workspace skills root. Then add a staleness/archive curator. Only after all of that consider autonomous capture — and copy the rule that self-authored UPDATES to existing skills always require human review, since the reviewer drafts without reading what it is overwriting. Gate capture on deterministic predicates (substantial turn, foreground only, quiet period, never from cron/heartbeat/subagent) so the system cannot learn from its own scaffolding.
- ADOPT 'TWO LAYERS, TWO BARS' AS THE GOVERNING RULE FOR THE V2 CAPABILITY LIBRARY. Anything that costs prompt tokens, a core tool schema, or a config key on EVERY request reaches every turn and faces the strictest scrutiny; skills, plugins, and channels carry no such tax and that surface should grow freely. Corollaries worth stealing verbatim: validate config from manifest metadata WITHOUT executing capability code (so one broken skill cannot break boot and the dashboard can render config for things that are not loaded); build ONE shared `message` tool with per-channel action discovery instead of every suite registering its own send/reply tools; and rebuild registries as atomic generation snapshots swapped on config change rather than mutated in place.
- REPLACE RAVEN'S MCP-ISOLATION RULE WITH TOOL POLICY PLUS SEARCHABLE CATALOGS. Raven's hard rule that MCPs never touch the main agent, so every skill must declare its own sub-agent, is a real problem solved at high cost: it forces a sub-process per integration, makes every skill a code artifact, and turns delegation into the only isolation mechanism. The modern answer is layered: skills as load-time-gated prompt instructions, allow/deny tool policy plus per-agent skill allowlists, tool search/describe so a large catalog never puts every schema in the prompt, and sub-agents reserved for genuine delegation and blast-radius control. This single change is what makes markdown skills possible at all, so it is a prerequisite for the first recommendation rather than an independent one.
- GENERATE THE SYSTEM PROMPT FROM WATCHED WORKSPACE FILES INSTEAD OF COMPOSING IT IN TYPESCRIPT. Assemble from `AGENTS.md` (operating rules and standing orders with explicit Scope / Triggers / Approval gates / Escalation and a 'what NOT to do' section), `SOUL.md` (voice), `IDENTITY.md`, `USER.md`, and `MEMORY.md`, re-assembling on file change, with a `/context list`-style command showing raw vs injected size and truncation status. This makes personality and operating authority editable without a deploy, matches the convention that Claude Code, OpenClaw, Hermes, and claude-gateway have all independently converged on, and directly serves the 'extend without code' requirement for the parts of behavior the owner will tune most often.
- MAKE `raven doctor --fix` A FIRST-CLASS SUBSYSTEM AND STOP WRITING BACKWARD-COMPATIBLE CONFIG PARSERS. Adopt the rule that runtime code reads only the current config schema, and that every breaking config change ships with a migration that detects the old shape, explains it, backs it up, and rewrites it to canonical form. Add a config-error safe mode (a distinct exit code the supervisor will not restart-loop on, with the control plane still starting for inspection and repair). For a single operator who will reconfigure this system constantly, a self-repairing migrator is worth more than lenient parsing — and it prevents the compat cruft that otherwise accumulates permanently in a solo-maintained codebase.
- WRITE DOWN THE TRUST MODEL, THEN HARDEN THE UNTRUSTED-INPUT PATH STRUCTURALLY. State explicitly, in the repo, that Raven is local-first infrastructure for one trusted operator and that the dashboard is not a multi-user boundary — so 'no per-user auth' is a decision rather than an oversight. Then defend the paths that actually matter: treat all inbound channel and email content as untrusted; require pairing approval for unknown Telegram senders; never auto-inject externally-derived content into the prompt; run tool execution in an egress-restricted container (`network:none`, read-only root, drop all caps) for anything touching untrusted input; and audit outbound URL construction, since PromptArmor's zero-click exfiltration worked by appending user data to attacker-controlled URL query parameters and firing on a link preview. Accept that prompt injection cannot be detected reliably and spend the effort on boundaries instead.
- CALIBRATE SCOPE DELIBERATELY — COPY THE PATTERNS, REFUSE THE SURFACE AREA. OpenClaw is ~417k non-test lines with ~160 bundled extensions, ~160 contributors, corporate sponsors, ~3.4k open issues, and it self-rates 68% / 'Alpha' with 6% end-to-end coverage; its Telegram channel alone is ~60k lines. Raven is one technical user. The good news is that almost every pattern above is small — markdown skills are a loader, lanes are a queue, provenance is one enum column, standing intents are one table with a prefilter, the proposal queue is one table plus a hash check. Adopt OpenClaw's own guardrail list as Raven's too: no agent hierarchies, no planner trees, no heavy orchestration layers duplicating what the agent runtime already does, and no skill marketplace. Explicitly do NOT chase channel breadth, companion apps, provider breadth, or media generation.

### research:agent-frameworks — Agent orchestration frameworks & patterns, 2025–2026: what to delegate to the Claude Agent SDK runtime vs own in custom code, and the modern consensus on planner/executor decomposition (assessed for Raven, a single-user self-hosted "life OS")

By mid-2026 the orchestration debate has largely resolved, and not in favour of graphs. The two big model vendors both shipped code-first, loop-based SDKs with no graph DSL, while the graph frameworks spent the period adding durability underneath (LangGraph's per-invocation `durability: 'sync'|'async'|'exit'`, Pydantic AI's four co-maintained Temporal/DBOS/Prefect/Restate integrations, Mastra's `suspend()`/`resume()`). The reason is that decomposition moved inside the model: a single agentic model interleaves planning, action and reflection in its own trace, so the 2024 pattern of a planner call → executor call → reflection call now reads as overhead. Anthropic's own reconciliation is dynamic workflows — the model decides the decomposition but emits it as an inspectable, re-runnable JavaScript script that the runtime executes outside the conversation, with intermediate results in script variables rather than the context window. Their published comparison frames the whole question as 'who holds the plan': Claude turn-by-turn (subagents, skills), a lead agent turn-by-turn (agent teams), or the script (workflows). They pointedly refuse to prescribe orchestrator-worker versus graph, warning only that 'parallelism and specialization have to earn their coordination cost' — a warning the empirical work backs up, with a single agent reportedly matching or beating multi-agent systems on ~64% of benchmarked tasks at roughly half the cost and a fraction of the latency. Where explicit graphs survive in the literature it is with honest caveats: the scheduler-theoretic 'Graph Harness' proposal admits it has no experimental validation and concedes graphs are wrong for tasks needing runtime structural adaptation — which describes a life OS exactly.

The Claude Agent SDK is no longer a thin loop wrapper and this is the central fact for Raven. It spawns a supervised `claude` CLI subprocess exposing the entire Claude Code harness: sessions with persist/resume/fork/tag plus a pluggable `SessionStore` (with runnable S3/Redis/Postgres reference adapters and a conformance suite); subagents with per-agent tools, model, effort, MCP servers, skills, own auto-memory and `maxTurns`; 30+ hook events covering tool, permission, subagent, task, compaction, config and file lifecycles; filesystem Skills with progressive disclosure; local plugins bundling skills, agents, hooks, MCP servers and workflows; a two-tier memory system (human-written CLAUDE.md plus agent-written `MEMORY.md`); MCP with tool-schema deferral on by default up to 10,000 tools; structured outputs via JSON Schema; turn and USD budgets that now cover subagent spend; OTel telemetry; and a documented hosting model whose 'hybrid session' pattern Anthropic illustrates with 'a personal project manager with intermittent check-ins'. A grep of `packages/core/src` shows Raven uses none of `hooks`, `settingSources`, `resume`, `forkSession`, `sessionStore`, `outputFormat`, `skills`, `canUseTool` or `Workflow` — and has hand-built parallel implementations of transcript storage, compaction, idle detection, memory, skill loading, permission enforcement and execution logging. Two of those choices are already breakage risks: a bare-string `systemPrompt` forgoes all the harness's tool and safety guidance, and a hard-coded `permissionMode: 'bypassPermissions'` now needs `allowDangerouslySkipPermissions: true` and refuses to run as root in Docker.

The right line to draw is the turn/task boundary. Everything inside one agent turn — the tool loop, context management, transcript persistence, permission evaluation, subagent isolation, skill discovery, MCP handling, memory injection, cost accounting — should be delegated; the runtime does it better, keeps improving, and Raven's versions are strictly behind. Everything between and around tasks should stay Raven's, because the SDK genuinely does not provide it: there is no watchdog, no top-level session timeout, no retry policy, `query()` is not resumable mid-turn, and store mirroring is explicitly best-effort. That is where 12-factor agents still bites hardest — own your control flow, unify execution state with business state, launch/pause/resume with simple APIs, compact errors into context — and where the durable-execution vendors are right that a checkpoint is not the same as a guarantee ('Checkpointing says: I saved your state. You take it from here. Durable execution says: your agent workflows will run to completion.'). So Raven's task-execution engine should be reconceived not as a DAG planner but as a durable outer loop: each `query()` call is one journaled step whose resumption handle is the session ID, every externally-visible side effect is appended to an idempotency-keyed log before execution, retries are bounded, and 'ask the owner and wait, possibly for days' is a first-class suspend/resume primitive rather than an edge case. For extensibility, the mission's 'without writing code' requirement is only met by markdown: a new Raven capability should be a `SKILL.md` file in a plugin directory, not a TypeScript workspace with a build step. And OpenClaw — 385k stars, a single long-running Gateway holding warm sessions, routing on account/channel/sender/peer to select agent identity and trust domain, markdown skills with workspace > project > personal > bundled precedence, plus a plugin SDK and marketplace — is independent confirmation that Raven's architecture is the right shape, and a concrete template for the three places it diverges.

**Recommended adoptions:**
- **Draw the line at the turn/task boundary.** Delegate everything *inside* one agent turn to the SDK runtime: the tool loop, context/compaction, transcript persistence, permission evaluation, subagent spawning and context isolation, skill discovery and progressive disclosure, MCP connection and tool-schema deferral, memory injection, cost/turn accounting, telemetry. Own in Raven code everything *between and around* tasks: the task record and its state machine, scheduling and triggers, event ingress and routing, the idempotent side-effect log, retry/suspend/resume across restarts, approval workflows, and the UI. This is 12-factor factors 5/6/8/9/12 in Raven, and the SDK for the rest.
- **Stop starting cold. Pass `resume` and add a SQLite `SessionStore`.** Raven currently omits `resume`, `sessionId` and `sessionStore` entirely, so every Telegram message and every scheduled run gets an amnesiac agent. Persist the session ID on the Raven session/task row, pass `resume` on follow-ups, and implement a ~150-line SQLite SessionStore (copy `examples/session-stores/postgres/src/PostgresSessionStore.ts`, run the shipped `shared/conformance.ts` suite). Adopt Anthropic's 'hybrid session' hosting pattern, which their docs name for exactly this use case ('a personal project manager with intermittent check-ins'). Implement `listSubkeys` so subagent transcripts survive too. Monitor `{type:'system', subtype:'mirror_error'}`.
- **Delete `session-manager/session-compaction.ts` and `session-manager/message-store.ts`.** The runtime auto-compacts, emits `compact_boundary`, and exposes `PreCompact`/`PostCompact` hooks. Replace Raven's compaction logic with (a) a `PreCompact` hook that archives the full transcript to Raven's DB for the dashboard, and (b) a 'Summary instructions' section in Raven's CLAUDE.md telling the compactor what to preserve (open task objective, decisions and rationale, pending owner approvals, entities touched). Persistent rules must live in CLAUDE.md, not the initial prompt, because CLAUDE.md is re-injected after compaction and the prompt is not.
- **Move the capability library to `SKILL.md` + local plugins, and keep `RavenSkill` only for what plugins can't do.** A new capability should be one markdown file, not a workspace with a `package.json` and a build step — otherwise the 'extend without writing code' goal is unmet. Ship each Raven suite as a local plugin directory (`skills/*/SKILL.md`, `agents/*.md`, `hooks/hooks.json`, `.mcp.json`, `workflows/`) and load it with `plugins: [{type:'local', path}]`, which Raven already passes through. Set `settingSources: ['user','project']` so skills, rules and CLAUDE.md load at all. Borrow OpenClaw's precedence ordering (workspace > project > personal > bundled) for conflict resolution. Put the most important instructions at the top of each SKILL.md, because compaction truncates skill bodies from the end.
- **Replace `permission-engine/` and `bash-gate/` with `PreToolUse` hooks + permission rules + `canUseTool`.** A hook denial is enforced by the harness; a prompt instruction is not — the memory docs say this explicitly. Move Raven's rules to `permissions.deny`/`allow` patterns (`Bash(npm *)`, `mcp__gmail__send*`) plus a `canUseTool` callback that can route a high-stakes call to Telegram for owner approval. Critically: fix the hard-coded `permissionMode: 'bypassPermissions'` in `sdk-backend.ts` — TypeScript now also requires `allowDangerouslySkipPermissions: true`, and it refuses to run as root, which will break the Docker deployment. Prefer `acceptEdits` or `dontAsk` with an explicit allowlist, reserving bypass for genuinely isolated work.
- **Make hooks the event bus adapter instead of parsing raw SDK messages.** `execution-logger.ts` currently reconstructs history by string-matching streamed JSON and truncating tool inputs to 200 chars. Map hooks onto `RavenEvent` directly: `PostToolUse`/`PostToolUseFailure` → tool events, `SubagentStart`/`SubagentStop` → agent-task lifecycle, `TaskCreated`/`TaskCompleted` → task events, `Notification` → Telegram push, `PermissionRequest` → approval request, `Stop`/`StopFailure` → completion, `InstructionsLoaded` → prompt-provenance debugging, and `ConfigChange`/`FileChanged` → replace Raven's custom config hot-reload. Hooks run in Raven's process and cost zero tokens.
- **Use `outputFormat: {type:'json_schema'}` for every agent→system handoff.** Raven is Zod-first already; generate schemas with `z.toJSONSchema(schema, {target:'draft-7'})` (the SDK validates against draft-07 and rejects newer). Apply it to plan/task decomposition, digest extraction, financial categorisation and transcription summarisation. The SDK re-prompts on schema mismatch and returns `error_max_structured_output_retries` if it can't converge — treat `subtype==='success'` with a missing `structured_output` as a failure too. This removes a whole class of brittle text parsing.
- **Keep MCP isolation; change the mechanism.** Express it as `AgentDefinition.mcpServers` per subagent plus `disallowedTools: ['mcp__*']` on the main thread, inside ONE session, instead of spawning a separate `query()` per skill. That preserves the context hygiene the CLAUDE.md rule is protecting while letting the orchestrator actually synthesise across skills (agents-as-tools, not handoff). Then lean on tool search — it is on by default; set `ENABLE_TOOL_SEARCH=auto:5` if Raven's MCP surface grows — and rename MCP tools/skills for searchability (`search_ticktick_tasks`, not `query_ticktick`). Design against the published numbers: 50 tools ≈ 10–20K tokens, and selection accuracy degrades past 30–50 loaded tools.
- **Adopt code-execution-over-MCP for the high-volume integrations (Gmail, TickTick, Google Workspace).** The interesting operations there are find/filter/aggregate over many items, and today every item flows through context. Anthropic measured 150,000 → 2,000 tokens (98.7%) on an equivalent workflow by exposing MCP servers as a code API the agent imports and calls in a sandbox, keeping intermediate results out of context. Raven already has a `bash-gate` and Docker; this is a natural fit and also gives PII tokenisation before data reaches the model.
- **Don't build a static planner. Two-tier orchestration instead.** Tier 1 (default): a single strong agent with skills and tool search — Anthropic's 'parallelism and specialization have to earn their coordination cost', reinforced by the finding that a single agent matched or beat multi-agent on ~64% of tasks at half the cost and a fraction of the latency. Tier 2 (when a task genuinely needs many workers): enable the `Workflow` tool and let Claude write the orchestration as a JS script, then save it as a named, re-runnable routine. Reconceive `task-execution-engine.ts`/`dependency-resolver.ts` around that interface — an inspectable orchestration *artifact* the owner can read, edit and re-run — not a DB/YAML DAG the owner cannot author. If Raven keeps its own runtime, copy `agent()`/`pipeline()` and the 'fan out across many small agents preserves more progress on resume than one long agent' property.
- **Put the durability in a Raven-owned outer loop, and only there.** The SDK gives you none: no watchdog, no session timeout, no retry policy, `query()` is not resumable mid-turn, and store mirroring is best-effort. Follow Anthropic's own lesson ('minor system failures can be catastrophic for agents' without resumability — checkpoint progress and enable recovery without full restart) plus the Temporal/Restate journaling model: treat each `query()` call as one durable step whose resumption handle is the session ID, append every externally-visible side effect (email sent, TickTick task created, money moved) to an idempotency-keyed log before executing it, and bound retries. Do NOT try to make the LLM loop deterministically replayable.
- **Make suspend/resume-for-owner-approval a first-class primitive, not an edge case.** For a life OS, 'ask the owner and wait, possibly for days' is the main control flow. Copy Mastra's shape: a step declares a `resumeSchema`, calls `suspend({reason, requestDetails})`, the snapshot persists to storage across restarts, and `run.resume({step, resumeData})` continues it; expose `status === 'suspended'` and the suspended-step path in the dashboard. Restate's durable promises show the timeout must persist too, so the remaining time survives a restart. Wire the resume trigger to a Telegram inline-keyboard reply, and use `AskUserQuestion`/`canUseTool` for in-turn approvals that don't need to outlive the process.
- **Restructure event ingress around one warm session per domain, with explicit trust domains.** Follow OpenClaw's Gateway model and the channels design: hold long-lived sessions and inject events into them via `streamInput()`, rather than spawning a fresh agent per event. Follow Anthropic's recipe: ~20 representative queries (high-impact regressions show up immediately), LLM-as-judge with an explicit rubric, and periodic human review for subtle bias. ### research:memory-context — Memory & context architectures for personal AI, 2025–2026: file-first vs vector DB vs knowledge graph, and what actually works for a single-user "aware of everything" assistant

**The decisive story of 2025–2026 is a reversal by the people who invented agent memory.** Letta — the MemGPT authors, originators of the "memory blocks + archival vector store" model that most of the field copied — shipped **MemFS**, a git-backed directory of Markdown files, and made it the *default* memory system for all new agents on the Letta API and in local mode, with `/memfs enable` migrating legacy memory blocks into files. Meanwhile Anthropic's `memory_20250818` tool is literally a filesystem API (`view`/`create`/`str_replace`/`insert`/`delete`/`rename` under `/memories`), and Anthropic's own engineering guidance tells agents to recover state by reading progress files and git logs, explicitly stating "compaction isn't sufficient" and positioning agentic search (grep/glob over a file tree) as preferable to "embedding-based pre-inference time retrieval." Claude Code's auto-memory is an index file plus on-demand topic files. OpenClaw stores everything as plain Markdown with the design rule "no hidden state — the model only remembers what is written to files." Four independent teams, converging on the same substrate. Vector databases and knowledge graphs did not win the memory layer; they were demoted to *optional derived indexes* over files.

**The benchmark literature is not usable evidence for this decision.** An audit of LoCoMo found ~6.4% of the answer key wrong and its LLM judge accepting 63% of intentionally-wrong answers; Zep and mem0 published mutually contradictory numbers over the same dataset with implementation errors on both sides; and most damningly, a plain **full-context baseline (73%) beat the specialized memory systems (68%)** because LoCoMo conversations are only 16k–26k tokens and fit in a modern context window. mem0 itself now concedes "a 91.6 on LoCoMo does not tell you how the system performs on your workload." So the architecture choice has to be made on operational grounds. On those grounds the heavy options look bad for one user: self-hosting Zep means running Graphiti *plus* Neo4j/FalkorDB *plus* embedding and LLM infrastructure with per-episode extraction LLM calls, and the consensus read is that it is "overkill if you just want to store and retrieve memories." Self-hosting mem0 is three Docker containers (FastAPI, Postgres/pgvector, Neo4j); notably mem0 itself *removed* its external graph store in 2026 in favor of built-in entity linking for deployment simplicity. Raven would be adding a distributed-systems problem to solve a note-taking problem.

**But the most important finding is that "memory" is four different problems that the vendor category conflates, and only one of them is memory.** Raven's mission — "aware of everything the owner does and needs to do" — actually decomposes into: (1) **curated memory** — learned preferences, decisions, lessons; small, always in context, file-first wins outright; (2) **live state** — today's calendar, inbox, open tasks; must be *fetched fresh from the source at the moment of need*, never stored, because a remembered calendar is a wrong calendar (OpenClaw does this with a 30-minute heartbeat that runs a monitoring checklist of live tool calls in the main session, and cron "automations" for exact timing); (3) **the personal corpus** — years of email and messages the owner never dictated to the agent; this is the one place a real index earns its keep, and the working reference implementation (nbramia/LifeOS) uses SQLite FTS5 + local embeddings fused with Reciprocal Rank Fusion, entirely local; and (4) **prospective memory** — what the owner *needs to do*. This last one is where file-first memory genuinely fails, and the answer is not a better retriever: OpenClaw **compiles intentions out of the model** into deterministic state — time-based intents become cron rows the moment they are uttered, event-based intents become SQLite rows with keyword/embedding triggers matched by a deterministic prefilter with *zero model calls*, hard fire budgets (3), cooldowns (24h), and expiry (90d), because prospective recall decays as context grows and models drift into an always-remind heuristic and cannot be trusted to infer cancellation. Tellingly, OpenClaw **tried and retired** the obvious LLM approach — an "inferred commitments" feature that extracted follow-ups from conversation — and replaced it with explicit scheduled tasks. That is a real negative result from a shipped system, and it is the single most transferable lesson for Raven, which is a proactive assistant whose scheduler, digests and heartbeats will otherwise flood its own memory with scaffolding noise (OpenClaw's countermeasure: cron/heartbeat/subagent sessions are structurally barred from producing durable memory candidates, and recalled content is marked so a fact recalled a hundred times stays one fact).

**Recommended adoptions:**
- **Split "memory" into four kinds and never let them mix — this is the highest-leverage decision in the whole assessment.** (1) *Curated memory*: learned preferences, decisions, lessons. Small, always in context, Markdown files. (2) *Live state*: today's calendar, inbox, open tasks. Fetched fresh from the source at the moment of need, NEVER stored — a remembered calendar is a wrong calendar. (3) *Corpus*: ingested email/messages/files the owner never dictated. Indexed and searched on demand, never auto-injected. (4) *Prospective*: what the owner needs to do. Compiled into deterministic scheduler/trigger rows, not prose. Most "my assistant's memory is a mess" failure is one of these four being implemented as another. Raven has all four surfaces already (digest, gmail/google-workspace/ticktick suites, scheduler, TaskBoard) but no explicit boundary between them.
- **Make Markdown files under git the source of truth for memory, and SQLite a purely derived index.** This extends Raven's existing and already-correct philosophy ('DB stores runtime state only — filesystem is source of truth for definitions') from skill definitions to memory. The acceptance test is concrete and worth writing as an actual test: *delete data/raven.db, rebuild it from the files, lose nothing*. If that fails, the boundary is wrong. This is what Letta migrated TO (MemFS, default-on, `/memfs enable` to convert legacy blocks), what Anthropic's memory tool already is, and what OpenClaw and Claude Code do.
- **Adopt the tier model with explicit injection rules, and enforce a hard budget on the always-loaded core.** Instructions (human-written, always) / Curated core — MEMORY.md + USER.md (gated writes only, always, budgeted) / Episodic — dated daily notes + transcripts (never injected, searchable) / Prospective — intents + cron (injected only on trigger) / Review — dream diary (never injected). Copy Claude Code's harness-enforced budget mechanic: measure MEMORY.md after every write, warn near the limit, hard-error over it, strip frontmatter and HTML comments before measuring. Without an *enforced* budget a file-first core silently rots as its tail stops loading — that is Claude Code's documented limit #1.
- **Keep USER.md separate from MEMORY.md, write imperative directives, and supersede in place.** Preferences fail differently from facts: PrefEval (arXiv:2502.09597) found preference-following degrades sharply over long conversations even with retrieval, and HorizonBench (arXiv:2604.17283) found systems select an originally-stated preference after the user changed it. So: begin entries with Always/Never/Prefer; carry `<!-- observed: DATE | status: active|superseded -->`; and when a preference changes, rewrite it in place with the superseded entry kept adjacent — never append a contradicting active directive. Raven's memory already holds several owner preferences (no base64, no chained commands, UI affordances) that belong in exactly this format.
- **Compile prospective memory out of the model — and treat OpenClaw's retired "inferred commitments" feature as a warning, not a gap to fill.** Time-based intents become scheduler rows the moment they are uttered; event-based intents become SQLite rows with keyword/embedding triggers matched by a deterministic FTS prefilter with zero model calls and a candidate cap; aspirations stay in Markdown with review dates. Ship the anti-nagging defaults as structure, not prompt instructions: 24h cooldown, 3-fire budget, 90-day expiry, max 3 injected per turn, explicit lifecycle (pending→armed→fired→done/cancelled/expired), and cancellation that is ALWAYS explicit and never inferred. Rationale: prospective recall decays as context grows and models drift into an always-remind heuristic (TriggerBench arXiv:2606.23459), and proactive systems overact and mishandle cancellation (ProEvent arXiv:2607.17701). Raven's scheduler plus its unified TaskBoard are the natural compilation targets — this is mostly wiring, not new infrastructure.
- **Add session-kind gating before adding any memory features at all. For Raven specifically this is the single most urgent guardrail.** Raven is a *proactive* assistant: digest, scheduler, proactive-intelligence, and any heartbeat all generate agent turns continuously. OpenClaw bars cron, heartbeat and sub-agent sessions from producing durable memory candidates entirely, citing production audits where 'the overwhelming majority of auto-captured memories' were scaffolding restatements, heartbeat noise, and recall feedback loops. Without this, Raven's own automation will bury the owner's real preferences under its own exhaust within weeks — and the more proactive Raven becomes, the faster it poisons itself. Pair it with recall-loop prevention: structurally mark anything injected from memory so it is never re-extracted, so a fact recalled a hundred times stays one fact.
- **Store provenance as unforgeable SQLite columns and quarantine by tier — this is the missing foundation under Raven's existing "gmail hardening" spec item.** Origin class as a closed set (`owner` / `agent` / `untrusted` / `system`), written by classification code and never parsed out of memory prose, plus session kind, observed timestamp, and a supersession key. Then: untrusted content may be stored, indexed and explicitly searched, but is structurally barred from the curated core and from auto-injection; the only paths into the prompt are explicit tool calls and the escalation lane, both wrapped in untrusted-content framing. Raven ingests Gmail, web content, and files, so memory poisoning (OWASP ASI06; MINJA arXiv:2503.03704) is a live threat, and detection-based defenses measure poorly. Classify conservatively and never default to `owner`.
- **Build recall as two lanes so the common case costs nothing.** Lane 1, on every turn, zero model calls: bootstrap-inject MEMORY.md + USER.md within budgets (refreshed per turn so long sessions pick up consolidation without a restart); ranked search over the index scored as hybrid relevance × exponential recency decay (30-day half-life) × write-time importance (1–10); and trigger injection where entries carry short trigger phrases matched by a fast prefilter, capped at ~3 per turn. Lane 2, an escalation sub-agent, fires only when the message shows recall intent AND Lane 1 found nothing strong — because temporal and multi-hop questions are precisely where flat retrieval is weakest (LongMemEval arXiv:2410.10813). This maps perfectly onto Raven's MCP-isolation rule: Lane 1 needs no model and no MCPs; Lane 2 is a spawned sub-agent, which is already Raven's delegation model.
- **Carry ranking metadata as trailing HTML comments on the Markdown line, not in a sidecar.** `- Keep the gateway on loopback. <!-- trigger: gateway setup, network safety --> <!-- importance: 9 -->`. The file stays human-readable and hand-editable, the index is derived from it, and missing annotations simply leave NULL columns that rank neutrally. This is what makes 'the owner can fix the memory in a text editor' true in practice — which is directly load-bearing for Raven's 'adapt/improve/extend WITHOUT writing code' requirement.
- **Run consolidation as a scheduled background job with deterministic gates around bounded model judgment.** Stage and dedupe without writing; reflect without writing; then promote only candidates that pass ALL thresholds (score, recall count, query diversity) — so memory graduates because it kept being *useful*, not because it was written confidently. Remove untrusted/system candidates structurally before building the prompt. Accept the rewrite only if it preserves prior entries above a max-loss fraction, includes every promoted candidate's `Source: path#Lx-Ly` anchor, fits the budget, and parses; otherwise fall back to append-only. Sleep-time compute has quantitative support (arXiv:2504.13171) and reflection-with-citations follows Generative Agents (arXiv:2304.03442). This fits Raven's existing scheduler naturally and needs no new subsystem.
- **Make memory writes concurrency-safe and crash-safe now, before two writers exist.** Optimistic concurrency: capture the content hash when consolidation input is built, re-check it immediately before an atomic rename, abort to append-only on mismatch. Store the pre-image and append a human-readable diff to a review file. Raven will have a scheduler and a chat session writing memory simultaneously, and a lock that every text editor must respect is not an option. Letta's git-worktree approach is the alternative if Raven's memory directory is a git repo — which it should be anyway, for the free version history.
- **Add a pre-compaction memory flush.** Before compaction summarizes a long session, run a silent turn that writes unwritten durable context to the dated note, then suppress the reply. Otherwise compaction destroys exactly the observations that were about to become memory. Anthropic's guidance is blunt that 'compaction isn't sufficient' on its own, and this is the cheap fix.
- **Build the daily brief as scheduled live assembly, not retrieval.** At a fixed time, call the calendar/email/task suites live, compose the brief, deliver it, and write the output to a dated note — with nothing about today's volatile state entering durable memory. Follow nbramia/LifeOS on two details: order the sync phases by real dependency (entity resolution → relationships → content indexing), and keep empty results SILENT to prevent notification fatigue. A proactive assistant that pings with nothing trains its owner to ignore it. Use OpenClaw's decision rule for the split: exact timing and isolated execution → scheduled job; flexible context-aware awareness batched into one turn → heartbeat.
- **Index the ingested corpus, but only the corpus, and start with FTS5 only.** SQLite FTS5/BM25 needs no API key and closes most of the grep gap immediately; add local embeddings (llama.cpp GGUF or Ollama) plus Reciprocal Rank Fusion later if recall proves insufficient. This matters concretely for Raven: the owner is on a MAX plan with `claude` CLI auth and no ANTHROPIC_API_KEY, so any hosted embedding provider means a new paid dependency. Design so search degrades gracefully to keyword-only, the way OpenClaw does — the index should be an enhancement, never a dependency.
- **Do not adopt mem0, Zep/Graphiti, or a Letta server as Raven's memory layer.** Zep self-hosted means Graphiti + Neo4j/FalkorDB + embeddings + per-episode extraction LLM calls — 'at least three systems to provision, monitor, and maintain,' and widely assessed as overkill for storing and retrieving memories. mem0 self-hosted is FastAPI + Postgres/pgvector + Neo4j, hides extraction behind an API the owner cannot open in an editor, and its ADD-only design leaves stale and current facts competing on similarity score — bad for a life assistant where facts change constantly. Both violate 'easy to understand'; both add distributed-systems operations to a WSL2 box serving one person. Steal one idea from Zep instead: explicit, dated supersession of facts, which the file-first encodings give you for free.
- **Implement Anthropic's `memory_20250818` contract rather than inventing a parallel one, and put policy in the handler.** The tool is client-side, so Raven's core owns the handler — which is exactly the right place for session-kind gating, provenance stamping, path-traversal validation (canonicalize and verify containment; reject `../`, `..\`, `%2e%2e%2f`), size caps, and view paging. Enforcing policy in the handler means the model cannot bypass it. Note the API auto-injects a memory protocol telling Claude to check its memory directory before anything else and to assume interruption, so the handler must be fast and must return a valid empty listing rather than an error on a cold store.
- **Treat memory auditability as a product feature, not a debugging aid.** Every consolidation writes a summary and pre-image trail; the dashboard shows what entered long-term memory and from where; the owner can read, edit, or delete any of it in a text editor. Raven's mission explicitly requires adapting and improving *without writing code* — and editing a Markdown file is the only memory-correction interface that actually delivers that. Raven already has a `/logs` page and a session debug API, so the surface pattern exists; extend it to memory. This is also the strongest argument against every hosted alternative, and the reason plain Markdown is currently the most portable format available given that no memory interchange standard has settled.

### research:life-os-landscape — The life-OS / proactive personal-assistant landscape, 2025–2026: proactivity patterns, life-modeling hierarchies, permission/trust models, and what separates the survivors from the abandoned

The category consolidated hard between late 2025 and mid-2026, and it consolidated around a shape Raven mostly already has — but with three layers Raven appears to be missing. The two dominant open projects are OpenClaw (formerly Warelay → Clawdbot → Moltbot; 385,340 stars, 81,009 forks, pushed daily) and Nous Research's Hermes Agent (226,395 stars, released 2026-02-25). Both are self-hosted, messaging-channel-first (Telegram/WhatsApp/Signal/Slack), file-based for definitions with SQLite for runtime state, and organized around a single long-lived gateway daemon plus per-agent workspaces. Daniel Miessler's PAI was renamed LifeOS (17,179 stars) and is the closest philosophical cousin to Raven's stated mission: it is explicitly a "Life Operating System" layered on Claude Code, with a TELOS goal hierarchy, a Pulse daemon on port 31337, and a Next.js life dashboard. Khoj (36,324 stars) is alive but its cadence has thinned to bursts (a single push on 2026-08-02 after nothing since 2026-06-24) and it has drifted toward RAG/second-brain rather than acting on your life. gptme (4,374 stars) stayed small and healthy by staying a terminal agent and pushing the "life OS" part into a separate forkable workspace template — which notably ships a Claude Max/Claude Code autonomous-run backend nearly identical to Raven's execution model.

On proactivity, the state of the art has converged on a specific, non-obvious decomposition that almost nobody got right on the first attempt: separate the *authority* to act from the *trigger* that fires it, and default the whole system to silence. OpenClaw splits this five ways — Automations (exact cron, isolated session, always creates a task record), Heartbeat (approximate ~30min main-session turn, no task record, replies `HEARTBEAT_OK` and is dropped if the remainder is ≤300 chars), Standing Orders (permanent authority declared in markdown `AGENTS.md`), Standing Intents (prospective memory compiled out of the model into cron rows or SQLite trigger rows), and Hooks. LifeOS ships a `notification-governor` whose header states the finding plainly: "alert fatigue is the dominant failure mode — cap nudge volume structurally before building anything else" — max 3 voice pings/day, 24h dedup by content fingerprint, quiet hours 22:00–07:00, and per-source auto-suppression after 2 false alerts in 7 days. Critically, both projects have *retired* the naive version of ambient awareness: OpenClaw's "inferred commitments" experiment (extracting follow-ups from conversation and delivering them via heartbeat) is dead, removed by `doctor --fix`, and its default heartbeat prompt now explicitly says "Do not infer or repeat old tasks from prior chats." Commercial products landed in the same place: ChatGPT Pulse (Sept 2025) runs one asynchronous overnight pass and delivers a bounded set of tappable cards rather than streaming interruptions.

The maintenance-burden thesis is confirmed, but with an important correction: what kills these projects is not custom orchestration per se, it is *accretion of bespoke scaffolding around a moving model*. The AutoGPT/BabyAGI/AgentGPT wave is dead in product form (AgentGPT development stopped Nov 2023, parent pivoted Jul 2024, 130+ unaddressed issues; AutoGen/AG2 moved to community maintenance with releases stalled), and the industry settled on supervised, bounded, evaluated agents. AutoGPT itself removed external vector-DB support after discovering brute-force similarity search over ~100k bits was milliseconds-fast — a canonical case of over-engineered infrastructure that then had to be maintained. HumanLayer, the reference human-in-the-loop SDK, superseded its own SDK with CodeLayer (a coding-agent IDE) and its main repo has gone quiet (last push 2026-06-19) while the durable artifact is the 12-factor-agents *document* (25,097 stars, frozen since 2025-09-21). Mycroft AI is the sharpest counterexample to a purely technical diagnosis: OVOS's postmortem notes Mycroft "was never formally abandoned" — the company kept the name, infra, and cloud services while development slowed, the community was sidelined, and sustaining contributions were rejected. Meanwhile the survivors all practice deliberate deletion: LifeOS v7.0.0 ("The Bitter Pill Release") cut always-loaded context from ~88KB to ~28KB, retired its modes/tiers system, and folded ~16 hooks into per-event dispatchers, on a single test — "would a smarter model make this rule unnecessary?" OpenClaw refuses config-compatibility aliases entirely, requiring a `doctor --fix` migration instead, and its VISION.md explicitly declines to merge "agent-hierarchy frameworks (manager-of-managers / nested planner trees) as a default architecture" and "heavy orchestration layers that duplicate existing agent and tool infrastructure." **Recommended adoptions:**
- Add a TELOS-style life layer above projects. Raven's v2 hierarchy stops at projects/tasks, which lets the assistant be busy without being aligned. Adopt LifeOS's chain — Current State / Ideal State per life dimension, then Mission → Problems → Goals (measurable) → Challenges → Strategies → Projects — as ONE canonical markdown file per Raven's filesystem-source-of-truth rule, with a generated short summary that is what actually loads into agent context. Copy the freshness convention (`<!-- updated: YYYY-MM-DD by:who -->` per section, surfaced as staleness in the dashboard) and populate it via a conversational `/interview` flow, never a form. Note LifeOS's explicit reversal: they split this into per-topic files and then consolidated back, and now tell users not to re-split.
- Build the notification governor BEFORE adding any more proactive sources. This is the single highest-leverage adoption and LifeOS states the rationale in code: 'alert fatigue is the dominant failure mode — cap nudge volume structurally before building anything else.' Route every proactive emission in Raven (proactive-intelligence, digest, gmail, financial-tracking, scheduler) through one governor enforcing a daily cap, 24h dedup by content fingerprint, quiet hours with non-critical messages queued to morning, per-source auto-suppression after repeated false alerts, and priority tiers where only `critical` bypasses caps and quiet hours. Log every suppress decision so the owner can audit what was withheld.
- Split proactivity into heartbeat versus automations, and give heartbeat a silence contract. Raven has a scheduler; it needs the second mechanism and the discipline. Heartbeat = an approximate periodic main-session turn with full context, no task record created, whose default prompt says 'do not infer or repeat old tasks from prior chats' and whose reply is dropped unless something genuinely needs attention (OpenClaw's `HEARTBEAT_OK` + ≤300-char suppression budget). Automations = exact cron, isolated session, always creates a task record. Implement heartbeat AS a system-owned scheduler job so Raven has one timer subsystem, not two, and add the deferral guards: skip when the main queue or another run for the same agent is busy, and honour active hours. Given Raven runs on MAX-plan CLI auth, copy OpenClaw's rate-limit-aware default of 1h rather than 30m.
- Introduce Standing Orders as Raven's primary no-code extension surface. This is the direct answer to 'adapt/improve/extend without writing code'. A standing order is markdown declaring a program's Scope (authority), Triggers, Approval gates, Escalation rules, and an explicit 'What NOT to do' list, auto-injected into every session; a scheduler job supplies the WHEN and references the standing order instead of duplicating it. Include the Execute-Verify-Report rule verbatim ('\"I'll do that\" is not execution'; 'Done without verification is not acceptable'; 3 attempts then escalate) — it targets the most common agent failure mode. Follow the stated best practice of starting with narrow authority and widening as trust accrues, and remember that 'standing orders without triggers become suggestions'.
- Compile intentions out of the model instead of storing them as prose. Add a prospective-memory layer to Raven's task engine: time-based intents ('remind me Friday') become scheduler rows at the moment they are uttered; event-based intents ('when the release lands, mention the changelog') become SQLite rows with machine-checkable trigger keywords, channel/sender scope, expiry, fire budget and cooldown, matched by a deterministic FTS prefilter on every inbound message with no model call in the matching path. Give them explicit lifecycle states (pending/armed/fired/done/cancelled/expired) and structural anti-nagging defaults (24h cooldown, 3-fire budget, 90-day expiry, max 3 injected per turn). Piggyback expiry maintenance on the existing scheduler hooks rather than adding another timer.
- Add provenance and taint to memory, and never let cron/heartbeat/subagent runs write durable memory. Raven ingests untrusted content through gmail, file-processing, transcription, and Telegram groups. Store an unforgeable origin class (`owner`/`agent`/`untrusted`/`system`) plus session kind as SQLite columns the model cannot write through prose, default unknown-provenance content to untrusted rather than owner, quarantine untrusted content so it can be searched explicitly but never auto-injects, and structurally mark recalled content so it is never re-extracted as new memory ('a fact recalled one hundred times stays one fact'). The governing principle to adopt: 'the write path is the security boundary' — content scanning of memory does not work, so gate promotion structurally.
- Replace code-plugin skills with bundle-style skills loadable at runtime. Raven's current 6-step skill procedure (new package.json + tsconfig + TS class + config/skills.json entry + root workspaces entry + rebuild) is the maintenance tax that kills single-maintainer systems and blocks conversational extension. Move to Hermes's model where a skill/profile is just a directory (SKILL.md + config declaring MCP servers and model + optional scripts), discovered at runtime with no build. Keep code plugins as the escape hatch for genuine runtime hooks only, and adopt OpenClaw's framing to decide which layer something belongs in: 'the core carries a per-call tax — each core tool, prompt line, and config key reaches every operator on every model request.' That is Raven's MCP-isolation rule generalized, and it should be written that way in ARCHITECTURE.md.
- Make approvals durable, graduated, and resumable from any surface. Model an approval as a suspended task row, not a blocking wait inside an agent session, so it survives `npm run dev:core` restarts — n8n's resumeUrl + form + max-wait-timeout triad is the proven shape. Offer allow-once / allow-always / deny (plus Activepieces' 'modify', which is the common case for drafts), attach expiry, and declare urgency and answer format structurally (`yes_no` / `multiple_choice` / `free_text` per 12-factor Factor 7) so the Telegram bot can render buttons instead of asking for free text. Enforce policy where execution happens, not where the request originates ('the host approvals document is the enforceable source of truth'), and make the approval message untruncatable — OpenClaw always prints the full request text precisely so terminal-width shortening cannot hide a malicious suffix.
- Adopt a graduated authority ladder rather than a binary trusted/untrusted switch. Start every capability at Tier 1 read-only + draft (nothing sends without approval), promote to Tier 2 act-under-its-own-identity-on-your-behalf, and only then to autonomous. gptme's GREEN/YELLOW/RED classification (code/tests/docs autonomous; email/social follow established patterns; financial/major decisions escalate) is a cheaper on-ramp Raven could ship this week and is a natural fit for Raven's financial-tracking and gmail suites.
- Fix the silent-failure class properly. Raven's CLAUDE.md already advises checking logs when a service silently fails to start — that is a symptom. Adopt LifeOS's three-state job model (running / installed / available) because 'a job that silently stopped looked exactly like a healthy one', add a poller-meta-monitor that alerts when an expected source stops producing, make the scheduled-work view read-only-by-construction with mutation kept behind its own confirmations, and add a `raven doctor` that reports each capability as live/broken/declined/stale and prints the exact fix command.
- Institute a deletion ritual and refuse config-compat aliases. Run Bitter Pill Engineering over CLAUDE.md, ARCHITECTURE.md, and every skill prompt on a schedule: for each rule ask 'would a smarter model make this unnecessary?', classify CUT/RESOLVE/MERGE/EVALUATE/SHARPEN/MOVE/KEEP, and keep only the four legitimate HOW classes (safety-gate, verified-gotcha, tool-contract, output-format-contract). LifeOS's v7.0.0 result — always-loaded context from ~88KB to ~28KB, modes/tiers retired, ~16 hooks folded into per-event dispatchers — is the payoff, and pairing the audit with a deterministic drift linter matters because 'drift grows back after every cut'. Separately, adopt OpenClaw's config policy: runtime reads the current schema only, and any breaking change ships a `doctor --fix` migration that detects the old shape, explains it, backs it up, and rewrites it. Compatibility aliases are how config code becomes unmaintainable.
- Do not grow the orchestrator; shrink it. OpenClaw — the largest project in this category — explicitly declines to merge 'agent-hierarchy frameworks (manager-of-managers / nested planner trees) as a default architecture' and 'heavy orchestration layers that duplicate existing agent and tool infrastructure', and the 2023 framework wave that built exactly those layers is dead in product form. Audit Raven's orchestrator, agent-manager, and event bus for logic the Claude Agent SDK already owns (control flow, retries, subagent spawning, compaction) and delete it. LifeOS and gptme both stayed alive by being a layer ON a harness rather than a competing harness; that is the strongest available argument for keeping Raven thin.
- Add ambient awareness only in the Conduit shape, or not at all. If Raven wants passive signal, copy the constraints exactly: stateless one-shot poll per invocation ('no long-lived daemon to leak or crash'), each adapter fault-isolated so one failure never aborts the poll, spans and metadata only and never keystrokes or content, a purely deterministic daily rollup with model narrative left as an explicit null seam for later, and lazy roll-up of every unrolled past day so a suspended WSL2 host loses nothing. And take the negative result seriously: OpenClaw retired auto-inferring follow-up commitments from conversation and now hard-codes 'do not infer or repeat old tasks from prior chats' — do not build 'guess my todos from chat'.
- Harden the boundaries rather than trying to win at injection resistance. Audits of OpenClaw found injected instructions are followed the overwhelming majority of the time; what determined actual damage was the boundary, not the model's resistance. Concretely for Raven: put agent containers on an internal Docker network with no direct internet and route egress through an allowlisting proxy (Hermes's documented defense against `curl`/`wget` exfiltration from tool-generated shell commands); wrap all externally fetched content in random-boundary delimiters with an injected security notice; classify data (health/finances/contacts as most sensitive) and enforce a per-route ceiling before any payload leaves for an external model; and define containment zones enforced at both write time and any publish/export path. Given Raven is one owner's whole life on a WSL2 host, the 135,000+ exposed OpenClaw instances and the ClawHavoc campaign that poisoned ~20% of its skill registry are the relevant precedents for never trusting a third-party skill by default.
- Publish a maturity scorecard for Raven's nine suites. Adopt OpenClaw's evidence-led model: a taxonomy of surfaces and capability areas scored on coverage, quality, and completeness with explicit bands, and the governing rule that 'an area does not become ready just because the implementation exists.' For a single owner this converts vague unease about which suites actually work into a prioritized list, and it is the mechanism that lets Raven grow capability count without growing untracked risk.
- Design proactive output as bounded, reviewable artifacts, not chat interruptions. Follow ChatGPT Pulse: one scheduled pass, output as a bounded set of cards with per-source opt-in toggles and an explicit feedback signal that tunes the next run. Pair it with the cheapest high-delight proactive primitive in the commercial category — follow up on a stated event ('you mentioned an interview Thursday; how did it go?') — which Raven's standing-intent layer enables directly. And make the Martin-vs-Town choice explicitly in ARCHITECTURE.md: narrow surfaces with an effortless Telegram front door, because every additional ambient source multiplies both maintenance and false-alert volume.

## Judge assessments

### judge:mission-fit — Mission fit — "central brain of my life": awareness of everything, reliable complex-task execution, and self-improvement over time (architectural ceiling, not bug count)

**Verdict:** Measured against "central brain of my life," Raven is today an amnesiac reflex arc, not a brain — and the shortfall is structural, not cosmetic. All three mission pillars depend on a loop the architecture never closes. Awareness: every chat turn is a cold agent — no transcript in the prompt (prompt-builder.ts reads only projectContextChain), no SDK resume anywhere (agent-backend.ts has no field for it; sessions.sdk_session_id is dead schema), and the only working memory store contains "(no memories yet)" after five months because nothing ever writes to it; the system cannot remember the previous message, let alone the owner's life. There is no world model at all — two disconnected project stores joined by string name-matching, no representation of people or commitments, and "remind me when X" has nowhere to live. Execution: the v2 task engine cannot complete a unit of work (onTaskCompleted is reachable only through an MCP that is never constructed), and — more damningly as a ceiling question — the design delegates completion-reporting to the model calling a tool rather than the runtime observing the outcome, so even the fixed version is fragile; meanwhile three parallel workflow engines hold half a working system each. Adaptation: five separate self-improvement mechanisms exist (retrospectives, memory MCP, scaffolding API, _agent-builder, config-approval chain) and not one connects end-to-end — retrospectives write to a knowledge graph agents can't read, scaffolded artifacts are inert until restart, and the agent-builder has neither Write nor Bash. The good news: the substrate choices (filesystem-as-truth, YAML definitions, event bus, memory-with-budgets) match where the field converged in 2026, and the fixes are wiring and deletion, not rewrites. But the honest verdict is that Raven's mission is currently satisfied only at the definition layer; the execution and feedback layers that would make it a brain are severed.
